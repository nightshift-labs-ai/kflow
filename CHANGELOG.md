## Unreleased

- **kflow: List static-key sites** has a Block column: the size of the out-of-line block at the site's target, as `bytes / insns`. It is decoded with `ida_ua.decode_insn` (no change to the database) from the target up to and including the first instruction that does not go on to the next one (IDA's `CF_STOP`; on arm64 `b` and `brk` by their bytes, never `b.cond`), and ends before a join (an instruction a jump or call reference reaches, not one kflow added), an x86 `int3` or the end of executable code: the block rule of `tools/reach.py`. At most 4096 instructions (then `+`); `?` where an instruction cannot be decoded. Worked out only when IDA asks for a row, once per target. Tested only with fake `ida_*` modules; not yet run in IDA. `tests/check_ida_api.py`: 226 checks; `tests/check_ida_names.py`: 95 names, none missing in the IDA 9.1 to 9.4 stubs.
- Pseudocode: when the hidden-path sentence fails at one site (an exception), that site's comment is shown without the sentence and the error is reported once in the Output window. Before, one such error dropped all of kflow's comments in that function. Tested with fake `ida_*` modules.
- Pseudocode comment of a static-key site: it now adds "nothing else in the database jumps or falls through to 0x..., so this pseudocode probably does not show that code" at a NOP site, or "the site is a jump here and nothing else in the database jumps or falls through to the next instruction 0x... (run when the key is on/off), so ..." at a site that is a jump, when, at the time the function is printed, the code the site does not run in this database (a NOP's target; the instruction after a site that is a jump) is an instruction with no ordinary flow into it and no jump or call reference except the NOP site's own and the references kflow recorded from sources that do not themselves jump there. A site that jumps to the very next instruction (`eb 00`) runs it in both key states: no sentence. Elsewhere the comment is as before. The flow part is what the test checks (fake `ida_*` modules); that Hex-Rays then leaves the code out is not checked in real IDA, hence "probably".
- Annotate (menu and `tools/kflow_headless.py`), with the Hex-Rays decompiler: a decompile check. kflow picks up to 20 functions with a static-key site that gets a new jump reference (spread evenly over those functions, the same every run; exception-table references are not checked), decompiles them before adding any reference and again afterwards, once IDA's auto-analysis has processed the new references (`ida_auto.auto_wait()`, with no time limit; from the menu, a wait box says kflow is waiting for IDA to analyse the new references) and after `ida_hexrays.mark_cfunc_dirty()`, so the second result is not the cached first one, and adds one line to the summary: all fine, or which functions decompiled before but fail after (each with Hex-Rays' own reason when it gives one, cut to 80 characters and `...`), with a pointer to **kflow: Remove annotations**. Functions that failed before are counted apart and not blamed on kflow. While IDA's auto-analysis is still running the check is skipped (the line says so): run **Remove annotations** and Annotate again after analysis to get it. The same when kflow's references from an earlier Annotate are still in the database. In `tools/kflow_headless.py` these lines, and the pointer to Remove, give its own steps instead (run with `--remove`, then again, without `--no-analysis` when that skipped the analysis). It decompiles for about 5 s before Annotate and starts no new decompile once about 5 s more have passed after it (a slow function can stretch either part; functions over 16 KB are not picked); any error in the check gives `decompile check skipped: <reason>` and Annotate goes on. Prompted by a judge-style review: nobody has checked what Hex-Rays does with kflow's jump references from NOP sites. Tested only with fake `ida_*` modules (a fake decompiler that can fail chosen functions always or only after Annotate, with a cache); not yet run in IDA.
- `tools/reach.py` measures what kflow's references add (results in `tools/reach_results.md`, rules checked by `tests/test_reach.py`): on the MemLens demo kernel, 96% of the 8,349 static-key NOP sites jump to code that no direct branch targets and no instruction falls into (8,011 out-of-line blocks, 264 KB), so kflow's reference is the only one that leads there; the same holds after 90% of the 7,504 WARN traps (1.7 instructions on average up to the next jump or join). x86_64, needs objdump; about 15 s per kernel.
- `--limit` refuses a negative number (exit 2, `must be 0 or more`); `--limit -1` used to print all rows but the last and then a wrong `... N more` count.
- `python3 -m kflow <kernel> --json out.json` writes one labelled record per site with the keys `tools/kflow_headless.py --json` uses (BUG/WARN: `addr`, `kind`, `function`, `file`, `line`, plus `flags`; static key: `addr`, `key`, `kind`, `target`, `function`, without the headless `now`, which needs IDA; exception table: `addr`, `fixup`, `type`, `handler`, `function`), with the ELF's symbol names and hex-string addresses. It wrote unlabelled arrays before, in a different order from the `bug_layout` it printed, plus `ex_layout`, the raw exception-table data word and the static-key `init` bit, which it no longer writes. Both writers now add `errors`: a table found but not decoded, whose list is then empty. 19,758 records on the MemLens demo kernel.
- Features (docs/FEATURES.md): Go to oops/WARN line says that a `BUG: KASAN:`, lockdep or hung-task report gives no match unless its first reliable stack entry is a BUG/WARN site.
- README: a shorter front door; the details moved to docs/FEATURES.md, docs/USAGE.md, docs/OUTPUT.md, docs/VERIFICATION.md and docs/limits.md (nothing removed); `tests/test_oops.py` checks the example `WARNING:` lines in docs/*.md too.

## v0.0.4 (2026-11-15)

- Annotate run while IDA's auto-analysis is still going no longer adds references from sites that are not instructions yet. The IDA SDK says the source of a cross-reference must be an item head and that `get_item_end()` counts unexplored bytes as 1-byte items, so on a freshly loaded kernel kflow's "the fixup is the next instruction" test could not match: such exception-table entries (common on arm64 from 5.16 and at x86's plain `rdmsr`/`wrmsr`, `EX_TYPE_RDMSR`/`WRMSR`) got a user jump reference that a later Annotate kept. Now a site that is not code (`ida_bytes.is_code(ida_bytes.get_flags(ea))`) gets its comment but no jump, data or static-key reference, and Annotate reports how many such sites there are and says to run it again after auto-analysis (also `tools/kflow_headless.py --no-analysis`). A later Annotate deletes a reference to the next instruction that an earlier one recorded (also one added by an older kflow), and reports it. This follows from reading the IDA SDK (`ida_xref`, `ida_bytes` stubs), not from a run in IDA; tested with fake `ida_*` modules only, which now model instruction heads (`get_flags`/`is_code`), real instruction ends where known and no functions while analysis runs. Found by a pre-release review of the IDA calls. `tests/check_ida_api.py` also checks `ida_bytes.get_flags` and `is_code`. When that later Annotate (or Remove) deletes such a reference and IDA's ordinary flow to the next instruction is gone afterwards (the SDK does not say whether `del_cref()` clears it), kflow puts the ordinary flow back (`fl_F`). On a database whose auto-analysis has finished, sites that are still not code are reported as "not code in IDA" with a hint to press C there, instead of "run Annotate again when auto-analysis has finished".
- Pseudocode comments when the Hex-Rays decompiler loads after kflow: kflow tried its pseudocode hook only when it loaded (and on Annotate), so a database annotated earlier showed no comments until Annotate ran again. IDAPython initialises its decompiler bindings when the decompiler plugin loads (`ui_plugin_loaded` in IDAPython's `py_hexrays.hpp`), so when the decompiler is not there at kflow's start, kflow now installs a `ida_kernwin.UI_Hooks` whose `plugin_loaded` tries again until the hook is in, and removes it when kflow unloads. Whether IDA loads the decompiler before or after kflow was not checked. This follows from reading the IDA SDK; tested with fake modules only (a fake decompiler that is missing at kflow's init and present later). `tests/check_ida_api.py`: 205 checks, 0 missing; `tests/check_ida_names.py`: 86 names, 0 missing in the stubs of IDA 9.1 to 9.5.
- New action **kflow: Go to oops/WARN line** and `python3 -m kflow <kernel> --oops <log>` (`-` for stdin; `--json` writes the match): paste a `WARNING:`, `kernel BUG at`, `RIP:` or `pc :` line, a whole oops or syzbot report, `func+0xoff` or `file:line`. kflow takes the function+offset (from the report's own `RIP:` / `pc :` line first, then the `WARNING:` or `kernel BUG at` line) and goes to the BUG/WARN site at exactly that address (a name the log prints without a Clang LTO suffix, `foo` for `foo.123`, `foo.llvm.N` or `foo.cfi`, tries all those functions, the plain one too; GCC's `foo.part.N`, `.isra.N`, `.constprop.N` and `.cold` are printed in full, so `foo+0x10` never means them; the output names the function used); if there is none it says so, goes to the log's address and lists that function's sites (those at the log's `file:line` first, then nearest first; the function as this file has it, whatever size the log prints (in IDA up to the end of its last chunk before the next name: code after a gap, such as after a WARN `ud2`, can be a tail chunk), and an offset past its end, from another build, lists them without going anywhere, also when the next function has a site at that address); with only a `file:line` shared by several sites it lists just those (in IDA: the BUG/WARN chooser with only those rows). When the log contradicts the site at its address (its `WARNING:` / `kernel BUG at` line names another `file:line` or kind; or that line has no `file:line` (a kernel without `CONFIG_DEBUG_BUGVERBOSE`) and its function+offset names another address than the `RIP:` / `pc :` line (`Kernel BUG at %pB` names a BUG at a function's first byte as the previous symbol plus its size: the same address); or, without a `WARNING:` / `kernel BUG at` line that names the site, it prints another function size than this file's, kallsyms' size to the next symbol counted: a log from another build, or two reports pasted together) kflow says `mismatch`, exits 1 and goes nowhere; it lists the sites at the log's `file:line`, else the site at that address (in IDA: a warning and the chooser). The same when the log names a function+offset this file does not have and its `file:line` has one site here (that line's site may be another one). A paste with several reports is cut into them (at `cut here` / `end trace`, the next `WARNING:` / `kernel BUG at` line, or another report's first line after a register dump; not at syzbot's repeated `WARNING:` line: syzbot prints a `WARNING:` or `RIP:` line once for each inlined frame, `func file:line [inline]`, before the one with the function+offset, which is the one used; not at `Kernel panic - not syncing:`: that line and the stack dump after it belong to the report in progress, so a `panic_on_warn` report, whose panic dump on x86 shows the trap's `RIP:` line again, counts as one; not at x86's executive summary after `end trace`, the trap's `RIP:` line and registers printed again, which belongs to the report before it); the first one with a `WARNING:` / `kernel BUG at` line or a trap `RIP:` / `pc :` line is used, and a note says how many there are. A `RIP:` / `pc :` line after the report's call trace began (x86 prints an interrupted context's registers where the trace crosses an IRQ or exception entry, as in a KASAN report from an interrupt) or after `NMI backtrace for cpu N` (another CPU's registers, in hung-task and RCU-stall reports) is not the report's trap, nor is a call-trace entry that repeats it (arm64 repeats the pc there). The trap's own lines after the trace are used, so the bottom of a report pasted alone still finds its trap: the executive summary of Linux 4.9 (`RIP  [<%p>] %pS`) and of 4.10 to 4.16 (`RIP: %pS RSP: %016lx`), and the `RIP:` right after the `#UD` entry frame `asm_exc_invalid_op` outside an NMI backtrace (panic()'s dump under `panic_on_warn`). A report with no `WARNING:` / `kernel BUG at` line and no trap `RIP:` / `pc :` line (KASAN, lockdep, hung task) or a pasted call trace of two or more entries counts only if its first reliable entry is itself a BUG/WARN site (that entry is a caller, not a trap); otherwise kflow says there is no BUG/WARN trap in it (naming such a `RIP:` / `pc :` line, if there is one) and exits 1; `?` entries are never used. `--oops` with `--list` or `--limit` is an error (exit 2); a module file named `foo.ko.debug` (Fedora / RHEL debuginfo) is module `foo`; in IDA a jump that fails (an address outside the database) gives a warning. On the demo kernel `file:line` alone matched four sites at `mm/userfaultfd.c:755`; `mfill_atomic_copy+0x674` picks `0xffffffff8e629bc4`. The line formats are taken from the kernel's printk calls (`__warn()` up to 6.18 and from 6.19, `report_bug()`, x86 `show_ip()` and call traces, arm64 `__show_regs()`, `%pS` with `[module]`, the 4.9 forms, 2.6 / 3.x `WARNING: at file:line func+0xoff()` and `Kernel BUG at <address>`) and from syzbot's reports (the source line syzbot appends after the symbol of a `WARNING:` / `Kernel BUG at` line is not taken as that line's `file:line`: for an inlined trap it is the outer frame's); the prefixes of `dmesg` (also `-T`, `-H`, `-d`, `-x`, `--time-format iso`), `/dev/kmsg`, `journalctl` (short, `-precise`, `-iso`, `-monotonic`) and `logcat -b kernel` (its time and level; logd makes the first word of a `pc :`, `lr :` or `RIP:` line the tag, so from logcat such lines are not recognised as `pc :` / `RIP:` lines) are removed, also before call-trace entries. `tests/test_oops.py`: log samples built from those formats; on each test kernel and module, a `RIP:` / `pc :` line made for every BUG/WARN site inside a function finds that site (for example all 24,386 on Android GKI 5.10; same-named static functions with a site at the same offset are listed as candidates; the 231 sites there in functions with a Clang LTO suffix also from the name the kernel prints, `cpu_replace_ttbr1` for `cpu_replace_ttbr1.989`: found, or listed among the copies of that name), also with the site's own `WARNING:` / `kernel BUG at` line before it, also with and from the line a kernel without `CONFIG_DEBUG_BUGVERBOSE` prints for it (`WARNING: ... at %pS`, `Kernel BUG at %pB`), and with another line or kind is a mismatch (among same-named functions: listed). The IDA action is tested only with fake `ida_*` modules (also a site in a later chunk of its function); not yet run in real IDA. In IDA only the function IDA shows under the log's name is tried (IDA names one function so); for a static function a note says that another one of that name is not tried, unless the log's `WARNING:` / `kernel BUG at` line confirms the site (a function whose name is neither public nor weak in IDA, `ida_name.is_public_name` / `is_weak_name`). When the site found in such a static function is a `mismatch`, the warning and a note also name that cause: `or IDA shows another static function of that name (IDA names only one)`. `tests/check_ida_api.py`: 205 checks, 0 missing.

- Annotate: a static-key target or fixup inside another IDA function (`ida_funcs.get_func`; not at its start, not in a tail the source's function shares, not the source function's own `.cold` part) now gets a user data reference (`dr_O`) instead of a jump reference (`fl_JN`), so that IDA is not asked to treat the other function's code as flow of this one (it could try to attach it as a tail chunk); other targets get the jump reference as before. - Experimental, off by default, x86_64 only: **kflow: Let WARN sites fall through (experimental)** and **kflow: Remove WARN fall-through**. IDA ends code flow at `ud2`, so the code after a WARN trap is unreachable and missing from the function. The action adds ordinary flow after exactly the WARN `ud2` traps of the kernel's `__bug_table` through a processor hook (BUG traps are left alone), lets IDA reanalyse them, appends newly reachable code that is in no function to the trap's function as a tail (never code of another function), and with Hex-Rays installs a microcode filter that decompiles those traps as a call to `__WARN()` that returns (unconfirmed whether Hex-Rays accepts it for `ud2`; if it refuses, the rest stays). The sites are recorded in the database as offsets from the image base; the hook is installed only for databases with that record, again whenever kflow loads one, and removed when kflow unloads. Prior art credited in the README: Jason A. Donenfeld's `linux_und.py`.   - The decompiler filter is installed only when at least one site got flow (if IDA ignored the hook, the action warns and installs nothing for the decompiler). Each function tail kflow appends is recorded with its end, and Remove takes out only a tail chunk that still starts and ends there and belongs to the site's function; a tail IDA merged with its own chunks (unknown whether IDA does that) stays and is counted.

## v0.0.1 (2026-11-12)

First release.

kflow reads three tables that every Linux kernel carries and IDA does not decode:

- `__bug_table`: every `BUG()` / `WARN()` trap (`ud2` on x86_64, `brk #0x800` on arm64; on x86_64 from Linux 6.19 a WARN with a message is a call, and kflow says so) with its source file and line, and whether the kernel continues after it (WARN) or not (BUG).
- `__jump_table`: every static-key site (a NOP or branch the kernel patches at runtime), its key and its branch target.
- `__ex_table`: every instruction allowed to fault and its fixup.

In IDA (**Edit > Plugins > kflow**): **Annotate kernel sites** comments every site and adds the jump references IDA cannot see (static-key targets, fixups) where IDA has none; **List BUG/WARN sites** lists every trap with its function and `file:line`; **Remove annotations** takes out kflow's comments and the references Annotate recorded adding (also after a rebase), and leaves earlier references (IDA's or yours) and your comments alone. `tools/kflow_headless.py` does the same through idalib, and `python3 -m kflow <kernel ELF>` decodes the tables without IDA.

Kernel modules (`.ko`) work too: the command line applies the module's relocations, and in IDA the tables are found by segment name. Static keys are named where possible: tracepoints as `tracepoint <event>`, dynamic-debug keys as `pr_debug file:line "format"` (8,898 of 9,237 keys on the demo kernel). Checked on five kernels and five modules outside IDA (README "What was verified": trap bytes, branch targets, source-file names): Debian 13 6.12 x86_64 (MemLens demo: 9,850 BUG/WARN sites, 9,237 static-key sites, 671 exception-table entries), a stripped Debian x86_64 `vmlinux` (tables found by section name), Android GKI 5.10.198-android12-9 arm64 (24,386 / 75,316 / 1,488; the 54,896 static-key sites outside init code that are compiled as a branch go to the decoded target); Android GKI 6.1.57-android14-11 arm64 (12,223 / 10,629 / 1,043); Debian 11 5.10.223 x86_64 (6,573 / 3,820 / 548; the older exception-table layout whose third field is a handler function: all 548 handlers are the kernel's `ex_handler_*` functions); module: Debian 13 `nf_tables.ko` (141 BUG/WARN sites, every `file:line` matches the v6.12.115 sources; 8 static-key sites with named keys) and Debian 13 arm64 `fat.ko`, `vfat.ko`, `ext4.ko`, `jbd2.ko` (676 BUG/WARN sites, every `file:line` on a BUG/WARN or assertion macro or a fortified copy in the v6.12.94 sources; 178 static-key sites, 174 of them tracepoints; 36 exception-table entries).

x86_64 and arm64, 64-bit kernels only. IDA API use: 64 names and object members checked against the official IDAPython stubs, 0 missing.

Built by an AI agent (Claude, operated by Nightshift Labs). Not yet run in real IDA.
